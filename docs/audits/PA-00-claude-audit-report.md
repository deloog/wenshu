## 3. 裁定审查：两选项独立重放（NF-03）

我不采信决策 #7 的依据陈述，独立评估两条路径：

| 维度 | 选项 A（导入期内容寻址重命名） | 选项 B（受控 Unicode 白名单 + 0.x 升级） |
|---|---|---|
| 冻结 Schema | **零变更** | **必须在 PoC-A 期间改动已冻结的 `document.schema.json`** |
| 消费者影响 | 无（`asset.path` 仍只出现白名单路径，下游零兼容分支） | 需重建生成物 + 重跑 document/template/host/project 四类契约（DoD §4 强制） |
| Unicode 规范化 | **无面**（原名仅为留痕字符串，永不落盘） | NFC/NFD 同名不同字节 → 需在 Schema/文件系统两侧定规范化，跨平台易分叉 |
| NTFS 大小写碰撞 | **无面**（名字由内容决定） | `A.png`/`a.png` 在 Windows 撞、Linux 不撞 → 跨平台行为分叉 |
| Windows 保留字符/设备名 | 规范化后天然规避 | 仍须逐项拒绝，白名单外还要叠加黑名单 |
| 幂等性 | 同内容重导入必得同名 | 依赖原名，重导入行为取决于原名是否变化 |

**独立判定：B 不优于 A，否决成立。** 三点是决定性的：

1. **B 会在 PoC-A 期间强行改动冻结 Schema**——这与项目自身的冻结纪律直接冲突，且按 DoD §4 会连锁触发四类消费者契约重跑，成本与风险都落在与 PoC-A 目标（排版验证）无关的方向上。
2. **B 引入的两类跨平台分叉我在 G1 亲历过**：G1-10 的 `FX-02` 正是"仅大小写不同的可移植身份"守卫，而我自己的探针也曾被 NTFS 大小写不敏感误导（G1-10 审计中如实记录）。B 等于把这类问题从 fixture 层扩散到用户资源层。
3. **A 未损失产品能力**：文件名语义并未丢失，只是从"路径"迁到"导入报告 + 语义审计留痕"通道；内容寻址是成熟做法（git 自身即如此）。PoC-A 的验证对象是排版，文件名语义不在其中。

**未发现 B 更优的场景**，故不提出反对意见。

## 4. 决策矩阵覆盖性试探（任务书要求构造未覆盖输入）

十行矩阵**逐行无矛盾**，规则间不冲突；六类任务书形态 + 四补充均有确定裁定。但我构造的输入中有三类**无法从现有规则得出确定裁定**：

| 我构造的输入 | 现状 | 为何是合理输入 |
|---|---|---|
| `assets/diagram`（**无扩展名**，内容为 PNG） | 矩阵零提及；§7.2 产出 `<hash>.<小写扩展名>`，**源无扩展名时该取值未定义**；且"媒体类型…与声明不符即拒绝"预设存在"声明"，无扩展名时无从比对——是取 sniff 结果还是直接拒绝？**歧义** | 剪贴板导出、部分工具产物常无扩展名 |
| `![](https://example.com/x.png)`（**远程 URL**） | **§7 及全文零裁定**（我精确检索 §7 区段与全文，均无 http/url/远程/下载/离线 相关裁定） | **首战楔形策略正是"用户已有 AI 草稿"**，而 AI 生成的 Markdown 极常含远程图片链接——这是最贴近真实输入的一类。按 R-DATA 本地优先与离线确定性，几乎必然应**拒绝**，但需明文 |
| `../../secret.png`、`C:\x.png`（**源路径穿越/绝对**） | 矩阵覆盖了文件名中的保留字符，但**未规定读取侧是否限制在导入根内** | 输出侧因内容寻址是安全的；风险在**读取侧**——导入器若按原路径取文件即可读出导入根之外 |

另：`gif/bmp/tiff/csv` 等非白名单类型仅由"扩展名白名单映射 png/jpg/jpeg/svg"**隐含**拒绝，而 webp 被显式列行并附"提示转换"。gif/bmp 在真实文档中与 webp 同样常见，建议一并显式化（否则实施者可能只对 webp 给友好提示）。

**这三类不是吹毛求疵**：任务书 §5 把"矩阵存在未覆盖合理输入"设为 FAIL 线，正是为了避免 PA-01 实施到一半遇到未定义行为再回头改政策。
