### MI-01（MINOR）· `G1-06 → G1-09` 的修正方向抹掉了真实依赖的最后痕迹

**事实**：检查 7 的处置为"只改消费者列（派生对象）"，其中 `G1-06` 的消费者列去掉了 `G1-09`。

但 `G1-09` 的任务行至今写着：范围内"…处理 **Host 复审 NF-02** 与 G1-07 m-05/NF-04"；完成证据"…**Host 值拒绝 NUL/控制字符及带任意前缀的盘符、POSIX/UNC、`file:` 和穿越片段**…"。二者都是 `G1-06` Host 契约的产物。而 `G1-09` 的依赖列自始为 `G1-03 → 全任务`，从未列入 `G1-06`。

**净效果**：路线图中现已**不存在任何结构性记载**表明 `G1-09` 依赖 `G1-06`，而 `G1-09` 自身散文证明它依赖。消费者列原本承担的"检出依赖列漏项"这一冗余作用，随该删除一并消失。

**起草方责任**：任务书 §3 声明"消费者列 = 派生校验对象、依赖列 = 权威手写源"，据此，消费者声明不被依赖链支持时删除消费者声明**是合规动作**。规格未预见"消费者声明可能才是真的那一方"，也未要求在散文证据冲突时先裁定。**此项过失属起草方，实施者按规格执行无误**，故定为 MINOR 而非 MAJOR。

**另三处经核未见同等证据**：`G1-03C → G1-08`（G1-08 范围内为"测试配置、worker 目录/端口构造器、证据目录"，未涉配置分层）、`A-01 → A-07P`（A-07P 范围内为 provider 契约与密钥安全存储，未涉 UI 状态机）、`A-02D → A-03`（A-03 范围内为文字/标题/列表/表格/图片编辑，未涉 docx 导入）。三处删除成立。

**关闭方式**：裁定 `G1-09` 是否确实依赖 `G1-06`。若是，在 `G1-09` 依赖列补入并重跑门禁；若否，在 `G1-09` 行注明其 Host 相关工作不构成对 `G1-06` 的任务依赖。同时建议在任务书补一条：消费者列与依赖列冲突且存在散文证据时，须先裁定哪一侧为真，不得默认删除派生侧。
