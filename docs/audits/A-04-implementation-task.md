## 3. 开工前必须裁定并回报的四件事

### D1　A-04 是不是 ADR-0013 说的那个「新的、独立的评估/实现任务」？（闸门级，最先裁）

ADR-0013 的出口只有两条，且要求**新开独立任务**：

1. **Chromium 路径**：在已签署的 User Startup VM 机制上取得首遍 TOC、稳定化重绘与 CJK 打印的正式 10 次分解，并**以输出不变为前提证明 ≤8 秒**；或
2. **Typst 路径**：完成文档模型适配器与 PDF 检查兼容性，再以同一 30 页输入、冻结字体、参考 VM、预热 +10 次、签署内容/几何/validator/CJK/双跑/SBOM **全部重审**。

**选项**：

- **A．A-04 就是那个任务**——范围扩写为「引擎路径证明 + 增量架构建设 + 预览整合」，工期与审计强度大幅提高；
- **B．另开独立引擎/增量架构任务（暂称 `A-04E`），关闭后 A-04 按原范围开工**；
- **C．拆分 A-04**——本棒只做**不接排版引擎**的部分（模板选择、预览状态机接线、取消与旧预览协调的 UI 层、检查结果呈现壳），分页实际接入留待引擎任务关闭。

**我的建议：B。** 理由是**可归因性**：把"引擎能否达标"和"整合是否破坏基线"放进同一棒，两类失败会纠缠在一起——停止条件写的是「若**整合**破坏 PoC-A 基线」，可现状是**引擎本就不达标**，届时任何红都无法判定归因，审计只能给不出结论。ADR-0013 要求"新的、独立的"任务，本身也指向 B。

若业主取 C，须同时裁定：**在引擎未接入的前提下，「真实 PDF 引擎」这条完成证据如何处置**（我的意见：只能标记为本棒不覆盖并顺延，不得用 fake 顶替）。

### D2　停止条件里的「已签署引擎」指什么？

「若整合破坏 PoC-A 基线，**回退到已签署引擎**」——但当前"已签署"的恰恰是**这条路径不达标**（PA-15 DEGRADE + 决策 #11A）。**回退目标本身不达标，停止条件无法执行。**

**我的建议**：裁定「已签署引擎」= PA-15 冻结的 Chromium 路径**连同其 `not_met` 结论**；A-04 的"回退"含义随之明确为**回到不接排版依赖的状态**，而不是"回到某个达标引擎"。这条必须写进 ADR-0031，否则停止条件是一句无法执行的话。

### D3　两个预算的口径与达不到时的处置

[增量分页探针](../pagination-incremental-evaluation.md)原文：**局部编辑后相关页面更新 ≤1s（交互性预算）**与 **30 页完整重新分页 ≤8s（后台批处理预算）**是两个独立指标，**不可相互抵消**；PA-13 的 24.300s `not_met` 不因增量成立而被追认。

**须裁定**：

1. A-04 的验收以哪个预算为准（我的建议：**两个都要**，分别实测、分别判定）；
2. 达不到时是**阻断**还是再 DEGRADE（我的建议：**阻断**——再 DEGRADE 一次等于把预算变成可协商项，而 ADR-0013 明写预算变更须另行批准）；
3. 测量必须在 **Win11 参考 VM**（PA-13 基线在那里），不得用 Win10 开发机——见 §6。

### D4　A-04 / A-04T / A-08 的边界

## 4. 硬边界（越界即停）

1. **不得接入或追认当前 Chromium 排版路径**（决策 #11A 原文）——D1 未裁定前，接入即越过已批准决策，**BLOCKER**。
2. **不得改预算、不得放宽检查契约、不得让引擎落地**（ADR-0013 原文），三者均须另行业主批准。
3. **不得改冻结 1.0.0**：`repaginationScope: const "incremental"`、`fullRepagination: false`、`stalePreviewRetained: const true` 已由 A-01 契约加固逐字钉死；`states-1.0.0.json` 的 `git diff` 必须为空。若实现需要全量重排，**停下报告**，那是契约变更。
4. **不得触碰 PoC-A 已签署冻结物**：fixture、字体清单、几何 oracle、检查契约、PA-12 门禁样本——字节不变。
5. **不得用 fake 顶替真实 PDF 引擎**；预览与检查的断言层必须打真实产物。
6. **分层**：`report-render` / `report-checks` / `template-*` / `pdf-*` 归 L1/L2，预览 UI 属 web 层，不得互相下沉/反向依赖（G2-03 门禁会拦）。

## 5. 验收标准与最低证据（D1/D3 裁定后生效）

| 完成证据（原文） | 最低证据 |
|---|---|
| **旧预览保留到新预览成功** | 端到端实证：新预览进行中 / 失败 / 被取消三种情况下，旧预览**仍在且可操作**；对应冻结 `stalePreviewRetained: const true`，须有决定性测试，变异（新预览开始即清空旧预览）必须变红 |
| **问题可定位** | 检查结果 → 文档节点的双向定位；定位到的节点在工作区中可聚焦（消费 A-03 稳定 ID） |
| **真实 PDF 引擎** | 真实引擎产物，非 mock；若 D1 取选项 C，此项**如实标记为本棒不覆盖并顺延**，不得用 fake 充数 |
| 可取消 | 取消后资源清理、主线程不阻塞；性能预算原文「取消后 **2 秒内**停止继续消耗主要计算资源为目标」 |
| 预算（D3） | 局部 ≤1s 与全量 ≤8s **分别**在 Win11 参考 VM 预热 +10 次实测，原始数据落 `artifacts/perf/<date>-A-04/`；机器证据按 §6「批次证据落盘规程」执行 |
| 停止条件（D2） | 「整合破坏基线」须有可判定定义 + 决定性测试 |

**变异自证**：至少覆盖「旧预览保留」「取消真取消」「问题定位不是假链接」，每条变异后**必须因正确原因变红**——红在别处即探针失效，作废重做（A-03 的 X1 探针首版就是因 fixture 太小而空转，作废重做才拿到读数）。

**测试层级**：单元 + 契约（模板/检查契约）+ 集成（真实渲染）+ **E2E（真实壳、真实引擎、真实文件）** + 性能采样（Win11 参考 VM）。

### 批次证据落盘规程（照抄执行，勿自行简化）

`--out` **只能改文件名、不能改目录**：`record-args.ts` 的 `OUTPUT_FILE_PATTERN` 拒绝任何含 `/` 的值，`record-environment.ts:9` 把输出目录硬编码为 `artifacts/reference-machine/`（[A-03-major-remediation §MAJOR-1 第 3 条](A-03-major-remediation.md)已登记，归口 G1-14 收口）。因此**没有任何参数能让它直接写进批次目录**，必须落盘后搬运：

1. `pnpm env:record --out environment.a-04.json`（**带 `--out`**；裸跑会直接覆盖签署基线）；
2. **立即**把该文件移入 `artifacts/perf/<date>-A-04/environment.json`；
3. 核 `git status --short artifacts/reference-machine/` **为空**——注意**不能只核 `git diff`**：新生成的 `environment.a-04.json` 是 untracked，`git diff` 看不见它，只有 `git status` 能发现遗留；
4. 移动后跑一次 `pnpm environment:check` 确认通过。

**第 2 步与第 3 步之间存在一个瞬时破门禁窗口**：`check.ts:68-72` 要求「machine labels must be unique across evidence files」，而新证据与 `environment.json` 同为 `wenshu-dev-primary`，未移走时 `environment:check` 必失败。**该窗口内不得跑 `pnpm verify` 或推 CI**，否则会得到一条与本棒无关的红。
