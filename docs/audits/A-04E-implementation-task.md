## 0. 起草结论

**A-04E 与 A-04 不同——它不卡闸门，卡的是"往哪走"没定。** 决策 #17 已授权本任务存在，DoR 的闸门项因此满足；但 [ADR-0013](../adr/0013-DEGRADE后排版引擎重评估.md) 给的是**两条并列出口**，走哪条（或先走哪条）尚无裁定，而两条的工作量、供应链影响与验收形态差一个数量级：

| | Chromium 路径 | Typst 路径 |
|---|---|---|
| 内容 | 首遍 TOC / 稳定化重绘 / CJK 打印的正式 10 次分解，**以输出不变为前提**证明 ≤8s | 文档模型适配器 + PDF 检查兼容性，再按同一 30 页 + 冻结字体 + 参考 VM + 预热 +10 次，**内容/几何/validator/CJK/双跑/SBOM 全部重审** |
| 供应链 | 零变动 | **须新入供应链**（lockfile/SBOM/许可/字体链复审，走决策 #12 同款流程） |
| 已知障碍 | 24.300s / 8s，超支集中在 render/分页段（PA-13） | 0.200s（快 100×）但 **10/10 被现有 `inspectPdf` 检查契约拒绝**（XMP 过滤不支持） |

**四件事须先裁定（§3 D1–D4）**，其中 D1 决定任务形态、D4 是 Typst 路径的前置阻断项。

## 3. 开工前必须裁定并回报的四件事

### D1　走哪条出口？（决定任务形态）

**选项**：

- **A．只走 Chromium**——分解 + 证 ≤8s（输出不变）；
- **B．只走 Typst**——适配器 + 检查兼容 + 全套重审 + 供应链；
- **C．两条都探，由 A-04E 出结论**（纯评估任务）；
- **D．分阶段**——先做 Chromium 的**正式分解**（有界、便宜、且无论走哪条都要的知识），据分解结果再裁定是否启动 Typst 路径。

**我的建议：D。** 三条理由：

1. **分解本身是无论如何都要的知识。** PA-13 已把超支定位到 render/分页段，并留下一句**假设**：「分页 24s **很可能**受 PA-11A 两遍 TOC 渲染 + 30 页 CJK 打印成本主导」——注意是"很可能"，**未经证实**。这个假设是否成立，决定 Chromium 是否有界可修，也决定增量架构的缓存边界画在哪。两条路径都需要它。
2. **成本不对称。** Chromium 路径供应链零变动、检查契约零变动；Typst 路径要动供应链、要补 XMP 检查兼容、还要把内容/几何/validator/CJK/双跑全部重审一遍。**在不知道 Chromium 能否修好之前先花大的，是把最贵的选项放在最前面。**
3. ADR-0013 把两条列为并列出口，**并未禁止排序**；先便宜后昂贵在期望成本上严格更优。

**风险如实登记**：若分解结论是"Chromium 无界可修"，则分解阶段的时间成为沉没成本。我认为可接受——那份分解数据在 Typst 路径下仍用于设定对照基线与缓存边界。

### D2　A-04E 是"评估任务"还是"实现任务"？

ADR-0013 原文是「评估**/**实现任务」，两者都在授权范围内，但验收形态不同：评估任务交**结论 + 证据**，实现任务交**可运行的引擎路径**。

另需澄清一处可能的误读：**修引擎性能 ≠ 接入排版依赖。** 决策 #11A 禁的是「Alpha 对当前 Chromium 排版路径的**依赖**」，那个依赖发生在 A-04 整合预览时；A-04E 在隔离环境里证明/优化引擎本身不构成依赖。**但这条请业主明确写进裁定**，否则实施者会因边界不清而自我设限或越界。

**我的建议**：D1 取 D 时，**阶段一为评估**（分解，只测不改），**阶段二的实现授权单独裁定**——阶段一结论出来后业主再决定是否授权动代码。

### D3　增量分页架构归 A-04E 还是 A-04？

**这条比它看起来重要。** 即使 Chromium 全量分页被修到 ≤8s，**1 秒的局部交互预算依然不满足**：[增量探针](../pagination-incremental-evaluation.md)实测局部编辑仍走完整管线，21 页耗时 4.613–4.919s（render 段 4.208–4.480s），离 1s 差一个数量级；且冻结 UX 1.0.0 的 `repaginationScope` 是 schema **`const: "incremental"`**、`fullRepagination` 契约级禁止——**A-04 无论如何都不能只交全量**。

**选项**：

- **A．A-04E 建增量架构 + 一次性验证工装；A-04 只做产品级预览 UI 整合**；
- **B．A-04E 只证引擎预算；增量架构归 A-04**。

**我的建议：A。** 取 B 会把"待建架构"重新塞回 A-04，而**可归因性正是决策 #17 拆分本任务的全部理由**——刚拆完又装回去，等于白拆。

**须一并裁定的接缝**：ADR-0014 列的四项「必须由真实编辑器验证」（旧预览后台可操作 / 局部编辑到受影响页 p95 / 全量重排取消的 UI 反馈与资源清理 / 分页级联与 TOC 页码与缓存失效的十次确定性对账）需要一个能跑的宿主。A-03 已提供真实编辑器，但预览 UI 属 A-04。**裁定：A-04E 可建一次性验证工装，且必须在实施记录中显式标注为工装、不得演化为 A-04 的产品 UI**——否则 A-04 会被架空、审计无从判断谁交付了什么。

### D4　Typst 路径的供应链前置（若 D1 涉及 Typst）

Typst **当前未进供应链**（`lockfile`/SBOM 含 `typst` 均为 0，仅隔离评估；Apache-2.0，官方 v0.15.1 Windows x64，SHA-256 与发布资产一致）。engine-reassessment 审计原文：「若入产品须另经批准/锁定/SBOM/字体链复审」。

**须裁定**：是否预先批准 Typst 进入供应链评估流程（走[决策 #12](../../决策记录.md) 批准 ProseMirror 的同款形态）。**这是前置阻断项**——不能等适配器写完才发现供应链没批。

## 4. 硬边界（越界即停）

1. **不得放宽任何预算。** 8s 全量 / 1s 局部 / 5s 检查 / 30s 导出均为 G0 冻结值；ADR-0013 原文「任何路径的**预算变更**……均须另行取得业主批准」。
2. **不得放宽检查契约。** Typst 的 10/10 拒绝是 `inspectPdf` 契约的真实判定；**修 Typst 去适配检查，不是修检查去接纳 Typst**。
3. **不得降质换时间。** PA-13 原文「**不得在本任务内降质凑过**」；Chromium 路径的 ≤8s 必须**以输出不变为前提**（ADR-0013 原文），须逐项对账内容/几何/validator/CJK。
4. **不得接入 Alpha 排版依赖**（决策 #11A）——本棒产出的是证明与架构，A-04 才是接入点。
5. **不得改冻结物**：`states-1.0.0.json`、PoC-A fixture / 字体清单 / 几何 oracle / 检查契约 / PA-12 门禁样本，字节不变。
6. **不得用一次性工装冒充产品 UI**（D3 裁定项）。

## 5. 验收标准与最低证据

### 5.1 Chromium 路径（若启动）

- **正式 10 次分解**：首遍 TOC、稳定化重绘、CJK 打印三段各自耗时占比，预热 +10 次，**Win11 参考 VM**；
- 若主张 ≤8s：须同时给**输出不变**证明——内容/几何/validator/CJK 逐项对账 + 双跑确定性；
- 若结论为"无界可修"：**如实结案**，附分解数据，不得为凑数改测法。

### 5.2 Typst 路径（若启动）

- 文档模型适配器 + `inspectPdf` 检查兼容（XMP 过滤）；
- 同一 30 页输入、冻结字体、参考 VM、预热 +10 次；
- 内容 / 几何 / validator / CJK / 双跑 / SBOM **全部重审**；
- 供应链按 D4 裁定的流程完成。

### 5.3 增量架构（若按 D3 取 A）

ADR-0014 四项逐条实测：

1. 旧预览在后台任务期间**保持可操作**；
2. 局部编辑 → 受影响页更新的**端到端 p95 ≤ 1s**；
3. 全量重排**取消**时的 UI 反馈、资源清理与主线程不阻塞（性能预算：取消后 **2 秒内**停止消耗主要计算资源为目标）；
4. 分页级联、目录/页码更新、缓存失效在参考 VM 的**十次确定性与正确性对账**。

**语料规模**：必须 **30 页 / 30,000 字**（冻结上限）。⚠️ [增量探针](../pagination-incremental-evaluation.md)当时跑的是 **21 页**——本棒不得沿用 21 页数据充当预算证据。

### 5.4 通用

- **测量机器**：Win11 参考 VM（`wenshu-poc-a-win11`），**不得用 Win10 开发机**——PA-13 基线在 VM，跨机不可比（[A-03-followups #3](A-03-followups.md) 同一个坑）；
- **批次证据落盘**：照抄 [A-04 任务书 §6「批次证据落盘规程」](A-04-implementation-task.md)四步，**G1-14 收口前不得裸跑 `pnpm env:record`**；
- **变异自证**：至少覆盖「输出不变对账」「取消真取消」「缓存失效正确」三项，每条变异须**因正确原因变红**，红在别处即探针失效、作废重做。

## 9. 独立审计的猎杀方向（预告）

1. **有没有为了达标而降质/改测法**——对比 PA-13 原始口径，语料、页数、字体、机器、预热与重复次数逐项对齐；21 页数据冒充 30 页结论即 BLOCKER。
2. **"输出不变"是不是真不变**——自建内容/几何/validator/CJK 对账，不采信汇总结论。
3. **检查契约有没有被放宽以接纳 Typst**——`inspectPdf` 相关文件 diff 必须可解释，放宽即 BLOCKER。
4. **预算有没有被悄悄改**——`performance-budgets.md` diff 必须为空。
5. **增量是不是真增量**——构造局部编辑，核是否只渲染受影响页区；全量管线仍在跑却报"增量"即造假。
6. **旧预览保留 / 取消真取消**——变异验证，红须落在对应断言。
7. **工装有没有冒充产品 UI**（D3 裁定项）。
8. **机器证据**——批次目录齐备，且 `git status --short artifacts/reference-machine/` 为空（签署基线未被覆盖）。
9. **冻结物零改动** + 台账同轮 + 报告随 PR 落盘 + 提交指纹逐位比对。
