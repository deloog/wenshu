### 2.4 r0 漏掉了"任务 ID 引用完整性"，而它是唯一能防静默断链的检查

r0 的 8 条检查中，只有旧检查 6 校验 §10 的任务 ID 存在；**依赖列、§3、§9、消费者列、台账的 ID 引用一律未校验，任务 ID 唯一性也未校验**。后果由实施者审计指出并经复验成立：

- 把依赖写成 `PB-O9`（字母 O）时，提取正则 `\d{2}` 不匹配，该 token 被**静默丢弃**——真实依赖消失，环检测与其余一致性检查全部照常通过。
- 把依赖写成 `PB-19`（格式合法但不存在）时，若不校验存在性，同样形成断链。
- `§4~§8` 出现重复任务 ID 时，以 ID 为键的映射会静默覆盖。

**这不是新想到的检查——我的原型脚本里本来就有**（E0「依赖不存在的任务」、D0「§3 引用不存在」、C0「§10 引用不存在」、H2「§9 引用不存在」），且四条实测均为 0 违反。**正因为是 0，我在把 34 条 findings 归纳成"8 条检查"时把它们当成"没内容"删掉了。**

教训须记录在案：**违反数为 0 的检查，恰恰是当前正在生效、正在守住这条线的检查。**归纳时按"当前有几处违反"取舍，会系统性地删掉最有效的那几条。

**1c 的实现必须限定在结构位置内。**实测全仓有 8 个"形如任务 ID 但未定义"的 token：`G2-M1`（G2-02 的里程碑编号）、`PA-A1`/`PA-A5`/`PA-A7`/`PA-A8`（PA-01 的发现编号）、`PA-06B`/`PA-11A`/`PA-11B`（实施期拆分）。它们全部合法，出现在散文与证据文本中。若对全文做拼错探测，会误报 8 处。结构位置的封闭定义见 §5.5。

### 2.6 检查 8 的规则与基线测的不是同一件事（r2，第二轮审计指出）

r1 把检查 8 的**规则**写成"每份审计报告必须被至少一行台账**引用**"，却用**另一种测法**给基线："报告文件名是否等于某个台账任务 ID"。两者不是一回事，因此 r1 的"违反 1 处"在自己声明的规则下不成立。

复核方按台账真实链接复算得 22 份未被引用；**我独立复算为 21 份**，差异在于把多少例外计入未引用（我实测 7 份例外未被链接，对方计 11 份）。**双方列出的 14 份非例外报告逐条一致**，核心发现完全成立。

我进一步按**台账行**而非报告数复算，得 **17 行**未链接自身审计报告——`G1-03` 已链接合并报告 `G1-03-to-G1-06`，但 `G1-04/05/06` 三行各自未链接，故行数多于报告数。r2 以行数为准，因为 8b 是逐行判定。

**处置**：拆为 8a（报告 → 台账条目，基线 1）、8b（台账行 → 自身报告链接，基线 17）、8c（链接可解析，基线 0），三条各自独立、各有实测基线，见 §5.4。

这是本任务书连续两轮被指出的**同一类缺陷**：r1 是"规则与基线不同源"，r0 是"检查表遗漏"与"例外用'等'字开放列举"。三者的共同点是**声明的口径与实际验证的对象不一致**——与门禁本身要防的问题同构。

### 2.5 一个必须记下的口径收窄

第一轮核查另报出 §10 矩阵与任务自述的归属不一致共 **64 处**（正向 16、反向 48，其中 14 处落在 §10 的两个散文兜底格"各任务测试""全部任务的范围外约束"）。

**本任务不修这 64 处，理由须记录在案而非静默略过**：

- §10 末尾的反向规则，其实际目的是"任何任务都必须有已批准的要求来源"——这一点由**检查 4 完整覆盖**，且当前 0 违反。
- 而"某任务算不算某需求的实现者"是**编辑判断**（主责 / 贡献性参与），路线图从未定义过口径。要求双向一致就是要求逐条裁定 64 处归属，其中大量落在已签署任务行的 `R-*` 标注上。
- 为满足一条从未声明的一致性要求而制造 64 处编辑，不成比例，且会动到已签署证据。

**裁定：§10 明确声明为编辑性覆盖摘要，不是派生索引。**该声明须写入 §10 本文，避免将来又被当成可校验对象。相应地，其任务 ID 的存在性由检查 1 覆盖。

## 3. 手写真源与被校验对象的划分

**权威手写源（三类）**

1. §4~§8 任务表的**依赖列**（直接依赖，语义须写入路线图本文）
2. 任务的 `R-*` 标注
3. §3.1 台账的**状态字段与证据链接**

**派生校验对象，不再视为并列真源（四项）**

| 对象 | 声明的语义 | 校验方式 |
|---|---|---|
| §3 关键路径 | 阶段主干的**编辑性摘要**，箭头表示"直接或传递前置" | 每条边须在依赖列中存在传递依据（检查 5）。**不生成**——"哪条链是关键路径"是人的编辑判断，不是图的输出，生成会毁掉编辑意图 |
| §9 并行波次 | 可并行组，**任务级** | 组内不得含任务与其直接依赖（检查 6） |
| 消费者列 | 真实传递下游的**子集**，不要求完备 | 声明的下游须在依赖链中存在（检查 7） |
| §10 矩阵 | **编辑性覆盖摘要**（§2.5） | 仅校验任务 ID 存在（检查 1） |

消费者列取"子集"而非"互为逆"，是刻意取舍：要求互为逆需修 131 处、大量在已签署行上；子集约束只需修 4 处，却仍能抓住真正的错误——声明一个在依赖链中根本不存在的下游。

## 5. 实现约束

1. **零新增第三方依赖。** 复用现成 devDependency `typescript` 与 Node 内建；不引入 markdown 解析库。参照 G2-03 复用 `collectModuleImports` 的先例。

2. **解析必须 fail-closed —— 本任务最重要的一条约束。** 检查器解析 markdown 表格，格式变动会让解析静默退化为"0 个任务、0 条边"，此时全部检查都会"通过"。因此必须：
   - 检查器输出解析计数（任务数、依赖边数、`R-*` 数、台账条目数、§3 边数、§9 组数）；
   - 计数低于登记的下限即**失败**（建议以 `1f53649` 实测值为基线登记：76 / 235 / 18 / 49 / 23 / 12，允许向上增长）；
   - 未能解析的表格行必须报错，不得静默跳过。
   这与 G2-03 要求输出"被扫描但导入列表为空的文件数"同源：**"跑过了"不等于"检查过了"。**

3. **例外只允许存在于显式登记表中，并 fail-closed。** 沿用 G2-03 的 `layering-registry.ts` 模式：
   - **已批准偏离**（检查 3）：登记 `{ 任务, 未满足的依赖, 依据 }`，如 `{ PA-15, PA-14U, 决策 C / PA-15 闸门报告 }`。未登记的不单调状态一律失败。
   - **审计报告例外**（检查 8）：见 §5.4 的封闭表，**逐条列举、不得使用"等"字**。
   - **历史波次**（检查 6）：登记 W1。
   登记表是单一手写真源，检查器只读它，不得在代码里另抄一份。r0 此处曾写"…`poc-a-poc-b-chain-integrity` **等报告**"，"等"是开放式列举，与本条的 fail-closed 自相矛盾——与本任务书 §2.5 批评 §10 散文兜底格（"各任务测试"）属同一类缺陷。r1 已改为封闭表。

4. **检查 8 拆为 8a / 8b / 8c，三条口径各自独立、各有实测基线。**

   范围仍收窄为 Claude 审计报告，不扩大到实施记录、ADR、闸门报告——本检查的目的是防止台账过期，而"任务已完成"的信号是**审计报告结论**；ADR 与实施记录是支撑证据而非完成信号（实施记录常先于审计存在，ADR 亦不按任务一一对应），纳入会制造大量误报。
